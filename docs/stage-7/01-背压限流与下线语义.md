# Stage 7：背压、限流与优雅下线语义

## 决策

阶段 7 使用本地令牌桶、现有每连接有界队列和 Gateway 内的 Backend 并发阀门；不引入消息队列或分布式限流器。它们不能改善单个 Gateway 的慢客户端/下游过载，反而会把拒绝策略、重试和运维状态变成分布式问题。

## 背压与限流

- 每个 Connection 的发送队列严格受 `SendQueueSize` 限制。
- 入站消息先经过每连接 token bucket，再经过 Gateway 全局 token bucket。超额消息直接丢弃并计数，不阻塞读循环；其他连接保持独立。
- 非可靠业务下行消息在发送队列满时按 `best_effort_queue_full` 策略丢弃。可靠消息、鉴权、错误、心跳和恢复控制消息不可丢；满队列时关闭慢连接，避免把关键语义静默丢失。
- Backend RPC 进入全局 `BackendMaxInFlight` 阀门。没有空位时立即返回 `backend_overloaded`（`retryable=true`），不建立等待队列，也不占用 goroutine 等待下游。

默认值：每连接 1000 msg/s、burst 200；Gateway 20000 msg/s、burst 4000；Backend 最大 1024 个在途 RPC。这些是保护性初始值，生产环境应按压测容量调整。

## 优雅下线

收到 SIGTERM/SIGINT 后：

1. Gateway 进入 Drain，拒绝新的 WebSocket Upgrade；
2. `http.Server.Shutdown` 停止监听并处理普通 HTTP 生命周期；
3. 已接收的业务请求允许继续完成；Drain 期间新业务请求返回 `server_draining`（可重试）；
4. 等待现有连接自行完成/关闭，最长 `DrainTimeout`（默认 10 秒）；
5. 超时后关闭余下连接并回收本地 Session、可靠消息和 Presence Lease。

`/metrics` 输出 `game_gateway_shutdown_total`、`game_gateway_rate_limited_total`、`game_gateway_messages_dropped_total` 和 `game_gateway_backend_rejected_total`，使发布与过载结果可观测。

运行参数：`-connection-rate`、`-connection-rate-burst`、`-global-rate`、`-global-rate-burst`、`-backend-max-in-flight`、`-drain-timeout`。
