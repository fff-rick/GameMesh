# Stage 6：多节点 Gateway 语义

## 范围与决策

本阶段只将 `UserID -> GatewayID / ConnID` 的短期归属状态放入 Redis；Session、Resume Token、Seq、ACK、Dedup Window 和 Pending 可靠消息仍由创建它们的 Gateway 进程持有。

因此，Resume Token 仍只能恢复到同一个、未重启的 Gateway。跨节点恢复和 Gateway 重启恢复不属于本阶段，避免在没有状态转移协议的情况下把内存 Session 错误地伪装为分布式 Session。

## 分布式租约

认证或本地 Resume 成功前，Gateway 以 `UserID` 创建一个 Redis 路由记录：

```text
key: {prefix}:user:{UserID}
value: { GatewayID, ConnID, LeaseToken }
TTL: PresenceLeaseTTL（默认 30 秒）
```

- `LeaseToken` 是每次 Claim 新生成的随机值，不会写入日志、协议或 Metrics label。
- Claim 使用 Redis Lua 原子地读取旧 Owner、写入新 Owner 并设置 TTL。
- Renew 与 Release 都用 Lua 比对 `LeaseToken`；延迟的旧节点无法续租或删除新 Owner，这就是 fencing。
- 只有活跃连接会续租。连接关闭时按 LeaseToken 条件释放；进程崩溃时由 TTL 自动清理，无需扫描。

Redis Pub/Sub 的 eviction 通知只用于尽快关闭被替换 Gateway 上的旧连接。通知可能丢失时，新 Owner 仍由原子 Claim 决定；旧 Lease 无法 Renew，故 Pub/Sub 不是一致性前提。

## 重复登录与失败边界

跨节点及同节点统一为 **New Login Wins**：最后一个成功 Claim 的连接成为 Owner。跨节点 Claim 成功后会向旧 Gateway 发布 best-effort eviction；同节点则直接关闭旧本地连接。

- Redis 在 Claim 前不可用：认证/Resume 返回 `presence_unavailable`，不创建或消费 Session；客户端可重试。
- Redis 在连接已建立后短暂不可用：续租后台重试，已有 WebSocket、Session 和 Backend 路由不被主动关闭。
- Redis 恢复而 Lease 已被别的节点替换或已过期：Renew 返回 fenced，Gateway 关闭该本地连接，防止双活路由。
- 节点崩溃：未 Release 的记录在 TTL 到期后自动消失；之后的新 Claim 不会继承长期陈旧路由。
- Resume 在本阶段仍需在原 Gateway 处理；它在重新绑定 Connection 前再次 Claim，因而同样遵循最后一次成功连接优先的策略。

## 配置与运行

空 `-presence-redis` 保持 Stage 5 单节点行为。启用多节点时，所有实例必须使用相同 `-presence-prefix`，且 GatewayID 必须唯一：

```bash
go run ./cmd/gateway -listen :8080 -gateway-id gateway-a \
  -presence-redis 127.0.0.1:6379
go run ./cmd/gateway -listen :8081 -gateway-id gateway-b \
  -presence-redis 127.0.0.1:6379
```

可配置项：`-presence-prefix`、`-presence-lease-ttl`、`-presence-renew-interval`、`-presence-timeout`。续租间隔应明显小于 TTL；默认值为 10 秒和 30 秒。

Metrics：

- `game_gateway_presence_leases`：本节点持有的本地 Lease 数；
- `game_gateway_presence_operations_total`：Claim、Renew、Release、Eviction、订阅和错误的计数。

UserID、ConnID 和 LeaseToken 不会成为 Metrics label。
