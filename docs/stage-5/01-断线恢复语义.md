# Stage 5：断线恢复语义

## 1. 范围与不变量

本语义只适用于一个仍在运行的 Gateway 实例。恢复状态保存在该进程内存中，因此连接到另一个 Gateway、Gateway 重启或进程崩溃后都不能使用本阶段的 Token 恢复。

- Resume Token 为服务端 CSPRNG 产生的不透明值，至少 128 bit 熵；禁止记录到日志或 Metrics label。
- 成功恢复必须复用原 SessionID 和 UserID，并轮换 Token；旧 Token 立即失效。
- 每个 Session 同时最多有一个已认证的有效 Connection。
- 恢复路径不访问 Router 或 Backend。
- Grace 过期必须同时删除 Session 和该 Session 的可靠性状态。

## 2. 控制协议

控制消息使用当前 protobuf-wire 编码；未知字段可以跳过，以保持兼容性。

```text
AuthResult {
  ok
  user_id
  session_id
  resume_token
  error_code
}

ResumeRequest {
  resume_token
}

ResumeResult {
  ok
  session_id
  resume_token
  error_code
}
```

- 初次认证成功：`AuthResult.ok=true`，携带 SessionID 和 Resume Token。
- 未认证 Connection 可发送 `ResumeRequest`。成功后该 Connection 立即绑定原 UserID / SessionID。
- 已认证 Connection 发送 ResumeRequest：`ResumeResult.ok=false, error_code=already_authenticated`。
- 空、错误、过期或已使用 Token：统一返回 `resume_token_invalid`，不泄漏具体原因。
- `ResumeResult.ok=true` 必须含新的 Resume Token；客户端应以新 Token 替换旧 Token。

## 3. 生命周期

```text
AUTHENTICATED
    |
    | 当前 Connection 关闭
    v
DISCONNECTED_GRACE
    | \
    |  \-- GraceDeadline 到达 --> EXPIRED（Session 与 Reliability 一起删除）
    |
    \---- 有效 Resume Token --> AUTHENTICATED（相同 Session，新 Connection，新 Token）
```

Connection 关闭仅在它仍是 Session 当前 ConnID 时才能使 Session 进入 `DISCONNECTED_GRACE`。因此旧 Connection 在恢复后才完成关闭回调时，不能删除或降级新的绑定。

普通认证仍是 New Login Wins：新的认证替换同一 UserID 的旧 Session，旧 Token 作废，旧 Session 的可靠性状态立即移除；这不是 Resume。

## 4. 恢复和业务处理顺序

成功 Resume 的顺序如下：

1. 在会话恢复临界区中查找 Token、确认未过期、替换 ConnID、清除 GraceDeadline、轮换 Token；
2. 将新 Connection 绑定为原 Session；
3. 先入队成功的 `ResumeResult`；
4. 获取该 Session 的 Pending 快照，按 `Seq` 递增重放；
5. 返回正常的 Connection 消息循环。

重放是同一逻辑消息的再次投递，不重新登记 Pending，也不分配新的 MessageID 或 Seq。每个重放 Envelope 保留原有的 MessageID、Seq、MessageType、RequestID 和 Payload。客户端需要继续按已有可靠消息语义 ACK。

Backend 不参与第 1--4 步。恢复后客户端发送的新业务请求才按正常路径重新执行 `UserID -> Room -> BackendInstance` 解析，并维持既有的超时和 `backend_unavailable` 错误映射。

## 5. Grace 与可靠性状态

进入 Grace 后，Session 的可靠性状态不会删除：已发送未 ACK 的 Pending、Seq、累计 ACK 与 Dedup Window 均保留。retry scanner 只处理有有效已认证 Connection 的 Session，因此 Grace 内不重传、不消耗 Retry 次数。

Session scanner 发现 `GraceDeadline` 已到时，先从 Session Manager 移除 Session，再从 Reliability Manager 移除同一 Session 的状态。这样 `ReliablePendingCount()` 不会因已过期 Session 残留而持续增长。

## 6. 并发与失败边界

- 两个 ResumeRequest 使用同一 Token 时，恢复操作串行化；第一个成功后 Token 已轮换，第二个请求必然得到 `resume_token_invalid`。
- 恢复与旧 Connection close 竞争时，以当前 ConnID 归属判断；旧 close 无副作用。
- 如果恢复响应或重放进入已满的发送队列，Connection 按既有 `send_queue_full` 策略关闭，Session 再次进入 Grace；不会伪造恢复成功后的可用传输。
- Gateway 主动关闭时直接终止所有 Session 和可靠性状态，不保留 Grace 恢复窗口。

## 7. 非范围

- Redis 或其他持久化存储；
- 多 Gateway 令牌路由与会话归属；
- Gateway 重启后的恢复；
- 跨节点可靠性状态转移。
