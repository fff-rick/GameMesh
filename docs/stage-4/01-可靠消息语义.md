# Stage 4：可靠消息语义

## 1. 目标与范围

Stage 4 在**单节点、当前 Connection 生命周期内**建立可验证的可靠消息基础：

- MessageID；
- Seq；
- ACK；
- 有界 Pending Queue；
- Retry；
- 有界 Dedup Window；
- Retry timeout 与最大重试次数；
- 可靠 / 非可靠 MessageType 分类接口。

本阶段不实现 Resume Token、Session Grace Period、断线后的 Pending 恢复、Redis 或跨 Gateway 状态共享。Connection 关闭时可靠性状态随当前 Session 一起释放，断线恢复属于 Stage 5。

## 2. 可靠性分类

`internal/reliability.Classifier` 决定某个 MessageType 是否采用可靠语义。

```text
DeliveryUnreliable
DeliveryReliable
```

默认分类器不把任何业务 MessageType 自动标记为可靠。需要可靠投递的业务类型必须显式配置，例如：

```text
1001 -> Reliable
1002 -> Unreliable
```

这样不会因为 Gateway 升级而偷偷改变旧客户端的协议行为。

典型建议：

- 聊天、关键指令、重要事件：Reliable；
- 高频位置、朝向、瞬时输入：Unreliable；
- “最新状态覆盖旧状态”的 Coalescible 语义仍保留给后续背压阶段，不在 Stage 4 实现合并队列。

## 3. 入站可靠消息：Client -> Gateway

可靠业务 Envelope 必须同时提供：

```text
MessageID != ""
Seq > 0
```

每个 Session 独立维护 `LastRecvSeq`，首条可靠消息的 Seq 必须为 1，后续必须连续递增。

### 3.1 正常接收

```text
expected = LastRecvSeq + 1
incoming.Seq == expected
```

Gateway：

1. 在进入 Backend 之前登记 MessageID / Seq；
2. 更新 LastRecvSeq；
3. 发送累计 ACK；
4. 只执行一次 Backend 路由。

ACK 是**传输层接收确认**，不表示 Backend 业务成功。Backend 成功或失败仍通过原业务响应 / ErrorResponse 表达。

### 3.2 重复包

同一 MessageID + Seq 再次到达：

- 不再次调用 Backend；
- 返回当前累计 ACK；
- 计入 dedup Metrics。

因此客户端因 ACK 丢失而重发同一 Envelope，不会在 Gateway 内重复产生 Backend 业务调用。

### 3.3 乱序包

如果：

```text
incoming.Seq > LastRecvSeq + 1
```

Gateway：

- 不调用 Backend；
- 返回 `reliable_out_of_order`；
- `retryable = true`；
- LastRecvSeq 不推进。

客户端应先补齐缺失序号。

### 3.4 冲突和过旧序号

- 同一 MessageID 对应不同 Seq：`reliable_sequence_conflict`；
- 同一 Seq 对应不同 MessageID：`reliable_sequence_conflict`；
- 已超出 Dedup Window 的旧 Seq：不重新执行业务，返回当前累计 ACK；
- MessageID 为空或 Seq=0：`reliable_invalid_envelope`。

Dedup Window 有固定上限。即使某条旧 MessageID 已被窗口淘汰，只要其 Seq 小于等于 LastRecvSeq，也不会再次进入 Backend。

## 4. ACK 语义

Stage 4 新增控制消息：

```text
MessageTypeAck = 15
```

ACK 使用 Envelope 自带的 `Ack` 字段，不增加额外 Payload。

Stage 4 采用**累计 ACK**：

```text
Ack = N
```

表示该接收方向 `Seq <= N` 的可靠消息已经确认。Gateway 收到客户端 ACK 后，从该 Session 的 outbound Pending 中移除所有 `Seq <= N` 的消息。

ACK 本身不进入可靠 Pending，不会对 ACK 再 ACK。

## 5. 出站可靠消息：Gateway -> Client

当某个出站 MessageType 被分类为 Reliable：

1. Gateway 生成唯一 MessageID；
2. 为当前 Session 分配单调递增 Seq；
3. 在真正入 Send Queue **之前**登记到 Pending；
4. 发送 Envelope；
5. 等待客户端累计 ACK。

重发时必须复用完全相同的：

- MessageID；
- Seq；
- MessageType；
- RequestID；
- Payload。

重发绝不能创建新的逻辑消息。

## 6. Pending Queue

Pending Queue 是每 Session 的可靠消息等待确认集合，受 `ReliablePendingLimit` 严格限制。

默认值：

```text
ReliablePendingLimit = 128
```

当 Pending 已满仍尝试产生新的可靠出站消息：

- 不允许继续增长内存；
- 记录 pending overflow Metrics；
- 当前 Connection 以 `reliable_pending_full` 关闭。

这里选择关闭而不是静默丢弃，是因为可靠消息已经声明“不允许丢”。

## 7. Retry

默认配置：

```text
ReliableRetryInterval = 500ms
ReliableMaxRetries    = 3
```

Server 使用一个全局 retry scanner，而不是每个 Connection / Pending Message 启动独立 goroutine。

每个 Pending 条目保存下一次重试时间和已重试次数：

```text
first send
  -> wait RetryInterval
  -> retry #1
  -> wait RetryInterval
  -> retry #2
  -> ...
  -> retry #MaxRetries
```

如果下一轮仍未收到 ACK：

- Pending 条目移除；
- 计入 retry exhausted Metrics；
- 当前 Connection 以 `reliable_retry_exhausted` 关闭。

不存在无限重试。

## 8. ACK 与重发并发

ACK 处理和 Retry 扫描都通过同一个可靠性 Manager 锁序列化 Pending 状态。

允许的边界行为：

- ACK 与某一次已经被 retry scanner 取出的重发发生竞争时，网络上最多可能仍出现这一条“已在途”的重复消息；
- ACK 一旦从 Pending 状态中生效，后续 scanner 不再继续生成新的 Retry；
- Client 必须按 MessageID / Seq 将重发视为同一逻辑消息。

这也是可靠协议必须具备 Dedup 的原因。

## 9. Seq 边界

Seq 使用 `uint64`：

- 0 表示“没有可靠序号”，禁止用于可靠消息；
- 从 1 开始；
- 达到 `math.MaxUint64` 后不允许回绕到 0 或 1；
- 再次分配时返回 sequence exhausted，并关闭受影响的可靠连接路径。

这样避免 wrap-around 把旧消息误认为新消息。

## 10. Connection 断开

Stage 4 尚未支持 Resume：

```text
Connection CLOSED
  -> Session TERMINATED
  -> reliability state removed
  -> Pending cleared
  -> Dedup state cleared
```

因此“ACK 前断线”在 Stage 4 的结果是：本连接不再继续 Retry，Pending 有界释放；Stage 5 才会将 Pending / LastAckSeq 与 Session Grace Period 结合，实现断线恢复。

## 11. Metrics

新增低基数指标：

```text
game_gateway_reliable_pending{gateway_id}
game_gateway_reliable_retries_total{gateway_id}
game_gateway_reliable_dedup_total{gateway_id}
game_gateway_reliable_out_of_order_total{gateway_id}
game_gateway_reliable_retry_exhausted_total{gateway_id}
game_gateway_reliable_pending_overflow_total{gateway_id}
```

仍禁止把 UserID、SessionID、ConnID、RoomID、MessageID、RequestID 作为 Prometheus label。
