# Game Gateway：方案调研

## 1. 项目定位与边界

Game Gateway
是多人在线游戏的客户端接入层。它负责连接生命周期、会话、鉴权、协议编解码、消息路由、心跳、限流、背压、断线重连与优雅下线，但不负责
Tick、玩家移动计算、碰撞、技能结算、AOI 或世界状态。

独立开发阶段的目标，是先把 Gateway 做成一个可以被任意 Room/State Sync
服务接入的通用实时网关。后续合并时，State Sync Server 只作为 Gateway
的一种下游服务。

## 2. 市面上是否有成熟方案

有成熟技术和项目可以参考，但建议"参考架构与实现思想，不直接套成最终项目"，否则会失去自己设计连接模型、Session、路由和可靠消息机制的学习价值。

### 2.1 Nakama

Nakama 是成熟的开源游戏服务器，服务端主要使用
Go，覆盖实时多人游戏、匹配、聊天、存储、社交等能力。它非常适合研究：

-   实时连接如何进入游戏后端；
-   Session 与实时消息如何组织；
-   authoritative multiplayer 如何与接入层协作；
-   Go 游戏服务器工程目录和运行模型。

本项目不直接基于 Nakama 二次开发，而把它作为"成熟游戏后端的架构参考"。

参考：

-   https://github.com/heroiclabs/nakama
-   https://heroiclabs.com/docs/nakama/

### 2.2 quic-go

quic-go 是生产级纯 Go QUIC 实现，可用于研究未来的 QUIC/WebTransport
接入。第一版不建议同时实现 WebSocket、TCP、QUIC
三套协议，应先把抽象层和核心链路做好。

建议顺序：

1.  WebSocket 作为第一接入协议；
2.  TCP 作为协议抽象验证；
3.  QUIC 作为高级阶段实验。

参考：

-   https://github.com/quic-go/quic-go
-   https://quic-go.net/

### 2.3 gRPC / Protocol Buffers

Gateway 与内部服务之间建议使用 gRPC + Protobuf。重点不是"会调用
RPC"，而是定义稳定的内部消息契约，使 Gateway 将来可以无感接入
Match、Chat、Room、State Sync 等服务。

参考：

-   https://grpc.io/docs/languages/go/
-   https://protobuf.dev/

### 2.4 Redis

Redis 可用于跨 Gateway 节点共享少量必要的路由/在线状态，例如：

-   UserID -\> GatewayID；
-   UserID -\> RoomID；
-   Session 恢复信息；
-   短期 Lease/TTL。

不建议把每个包、每次心跳都写 Redis。高频连接状态应优先保存在 Gateway
本地内存。

### 2.5 Prometheus / OpenTelemetry

成熟实时服务必须可观测。建议从项目早期就定义：

-   当前连接数；
-   建连/断连速率；
-   消息吞吐；
-   P50/P95/P99 延迟；
-   丢弃消息数；
-   Send Queue 长度；
-   心跳超时；
-   重连成功率；
-   下游 RPC 延迟和错误率。

参考：

-   https://prometheus.io/
-   https://opentelemetry.io/docs/languages/go/

## 3. 建议重点自行实现的部分

为了保证项目价值，以下部分建议自己设计，而不是直接依赖完整游戏服务器框架：

-   Connection 抽象；
-   Session 生命周期；
-   协议 Envelope；
-   Message Router；
-   本地 Session Registry；
-   ACK/Seq/Retry/Dedup 模型；
-   Backpressure；
-   Rate Limit；
-   Resume Token；
-   Session Migration；
-   Graceful Shutdown；
-   Gateway -\> Backend 路由模型。

## 4. 暂不进入项目范围

第一期明确不做：

-   游戏世界；
-   Tick Loop；
-   AOI；
-   客户端预测；
-   技能/战斗；
-   匹配算法本身；
-   聊天业务本身；
-   Kubernetes 自动扩缩容；
-   跨地域多活。

这些能力可以在 Gateway 稳定后扩展，或由另一个 State Sync 项目承担。

## 5. 调研结论

Game Gateway 的成熟技术基础非常充分。推荐技术路线是：

**Go + WebSocket + Protobuf + gRPC + Redis + Prometheus/OpenTelemetry**

其中 WebSocket 解决第一阶段客户端接入，gRPC 解决内部服务调用，Redis
只承担必要的分布式状态，可靠消息、Session 和路由机制自行实现。QUIC
留作高级扩展。
