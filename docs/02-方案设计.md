# Game Gateway：方案设计

## 1. 总体目标

构建一个独立的 Go Game
Gateway，使客户端只需要维护一个长连接，就能够完成鉴权、心跳、消息发送、断线恢复，并由
Gateway 将消息路由给后端服务。

最终合并目标：

``` text
Client
  |
Game Gateway
  |
  +-- Match Server
  +-- Chat Server
  +-- State Sync Server
```

## 2. 设计原则

1.  Gateway 无游戏逻辑。
2.  本地状态优先，分布式存储只保存必要状态。
3.  慢客户端不能拖垮整个 Gateway。
4.  后端服务故障不能无限堆积消息。
5.  协议必须支持版本演进。
6.  所有核心能力必须可压测、可观测、可故障注入。
7.  第一阶段优先正确性，再做性能优化。

## 3. 核心模块

### Connection Layer

职责：建立、关闭、读取和写入客户端连接。

要求：

-   每个连接有唯一 ConnID；
-   明确 read/write 生命周期；
-   写操作不能由业务 goroutine 无限制直接写 socket；
-   每连接拥有有界发送队列；
-   连接关闭必须可传播给 Session 层。

### Protocol Layer

定义统一 Envelope，至少在概念上包含：

-   Version；
-   MessageType；
-   RequestID/MessageID；
-   Seq；
-   Ack；
-   Payload；
-   Timestamp。

协议需要支持未知消息拒绝、版本不兼容处理、最大包大小限制。

### Session Manager

负责：

-   UserID 与 ConnID 绑定；
-   Session 创建/销毁；
-   重复登录策略；
-   LastSeen；
-   LastRecvSeq/LastSendSeq；
-   Room/Backend 路由信息；
-   Resume Token。

### Heartbeat

负责：

-   客户端存活判断；
-   Idle Timeout；
-   RTT 基础统计；
-   僵尸连接回收。

### Message Router

负责把不同 MessageType 路由给内部服务，不包含业务逻辑。

### Reliable Messaging

阶段性加入：

-   Seq；
-   ACK；
-   Retry；
-   Dedup；
-   重连后的缺失消息恢复。

并非所有游戏消息都要求可靠。例如高频位置类消息未来可以使用"新状态覆盖旧状态"的策略。因此协议层应预留可靠等级/消息语义的扩展空间。

### Backpressure

必须使用有界队列。

当客户端消费速度不足时，需要明确策略：

-   丢弃可丢消息；
-   合并状态类消息；
-   对可靠消息施加上限；
-   达到阈值后断开慢客户端。

### Service Router

负责维护：

``` text
User -> Room
Room -> Backend Instance
```

第一版可以静态配置；后续再引入服务发现。

## 4. 技术栈

  类别         建议
  ------------ -----------------------------------
  语言         Go
  客户端接入   WebSocket，后续 TCP/QUIC
  序列化       Protocol Buffers
  内部通信     gRPC
  分布式状态   Redis
  指标         Prometheus
  Trace        OpenTelemetry
  日志         Go structured logging
  压测         自研轻量模拟客户端 + 常规压测工具
  部署         Docker；后期可扩展 Kubernetes

## 5. 测试体系

### 单元测试

覆盖：

-   Session 状态转换；
-   Seq 比较；
-   ACK 确认；
-   Dedup；
-   Router；
-   Heartbeat Timeout；
-   队列满策略；
-   Resume Token 校验。

### 集成测试

至少覆盖：

1.  Client -\> Gateway -\> Fake Backend；
2.  连接建立与鉴权；
3.  心跳；
4.  后端 RPC 成功/失败；
5.  Redis 可用/不可用；
6.  客户端断开后恢复；
7.  Gateway 优雅关闭。

### 并发与竞态测试

必须运行 Go race detector，并针对：

-   Session 注册/注销；
-   同账号重复登录；
-   Close 与 Write 并发；
-   ACK 与重发并发；
-   Gateway Shutdown

设计专项测试。

### 性能测试

指标至少包含：

-   并发连接数；
-   每秒消息数；
-   P50/P95/P99 转发延迟；
-   CPU；
-   RSS；
-   GC；
-   goroutine 数；
-   单连接平均内存；
-   Send Queue 堆积。

不要一开始写死"10 万连接就是成功"。先建立基线，再逐阶段提高目标。

### 故障测试

注入：

-   客户端突然断网；
-   ACK 丢失；
-   Backend 超时；
-   Redis 短暂不可用；
-   Gateway 收到 SIGTERM；
-   慢客户端；
-   消息突发流量。

## 6. 最终验收标准

独立项目完成时应满足：

-   Gateway 不依赖具体游戏逻辑即可运行；
-   支持稳定长连接和鉴权；
-   Session 生命周期明确且无明显竞态；
-   支持心跳与僵尸连接回收；
-   支持统一协议与消息路由；
-   具备可靠消息基础能力；
-   支持断线恢复；
-   支持多 Gateway 节点的必要状态共享；
-   支持优雅下线；
-   有可复现的压测报告；
-   有故障注入测试报告；
-   State Sync Server 将来只需实现约定的内部接口即可接入。
